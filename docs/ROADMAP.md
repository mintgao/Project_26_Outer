# ROADMAP — Outer 五阶段路线图（精简版）

> 本文件是落进仓库的权威精简版路线图，**不依赖任何外部文档**，Agent 可直接据此判断阶段边界。
> **工期假设：1 人开发、每周投入 10–15 小时。** 周数为在此假设下的估算。
> 详细任务与验收标准见 `docs/TASKS.md`；当前所处阶段见 `docs/STATE.md` 的 `current_phase`。

## 阶段总览

| 阶段 | 名称 | 工期 | 核心目标 | 阶段门禁（必须全部达成） |
| --- | --- | --- | --- | --- |
| **Phase 0** | 止损与地基 | 1–2 周 | 消除高危安全项，建立可信工程基线 | 无高危项残留；CI 能跑且为绿色 |
| **Phase 1** | 可信闭环 | 5–7 周 | 跑通「录入 → 每日决策 → 打卡」并让人愿意用 | 录 20 件 < 5 分钟；推荐采纳率 ≥ 40%；7 日打卡率 ≥ 50% |
| **Phase 2** | 越用越准 | 6–8 周 | 从反馈中学习，推荐逐步个性化 | 第 4 周采纳率比第 1 周高 **≥ 10 个百分点** |
| **Phase 3** | 诊断与灵感 | 6–8 周 | 从「今天穿什么」延伸到「该买什么/怎么变化」 | 衣橱诊断被主动使用；灵感/分享有真实使用数据 |
| **Phase 4** | 规模化 | 按需启动 | 多用户、性能与成本、技术栈再评估 | 由 Phase 3 结果触发，无固定排期 |

## 🚧 阶段门禁（最重要的一条规则）

> **门禁不通过，不得进入下一阶段。** 不许「先做一点下一阶段的功能试试」。

尤其是 **Phase 1 → Phase 2**：如果推荐采纳率没到 40%，说明推荐**本身**还不被信任。
此时去做个性化与学习，**个性化只会放大一个本来就不被信任的推荐**——
把错误的推荐调得更「符合你的习惯」，用户只会更快放弃。
采纳率不达标时，正确做法是回到 Phase 1 改推荐规则（温度约束、配色规则、理由表达），而不是加模型。

同理，Phase 0 的安全与工程债不清完就做功能，等于在漏水的地基上盖楼：
密钥泄露、schema 不可复现、无 CI，任何一项都会在后面十倍偿还。

## Phase 0 — 止损与地基（1–2 周）

**目标**：把已知高危问题清零，让仓库进入「可信」状态。

- 轮换全部已泄露密钥；`.env` 移出版本控制并建立 `.env.example` 规范
- 收紧 RLS（`profiles` 按 `auth.uid()` 隔离）；Storage 桶转私有 + 签名 URL
- AI 代理加 JWT 校验、单用户日配额与结构化日志
- 重建干净的 migration 基线（现有 migration 已被污染）
- 建立三层目录骨架（UI / 数据层 / 领域层），开 TypeScript `strict`，生成数据库类型
- 配色引擎补单元测试；lint + build + test 接入 GitHub Actions
- **门禁：无高危项残留、CI 能跑（绿色）**

## Phase 1 — 可信闭环（5–7 周）

**目标**：核心循环「录入 → 每日决策 → 打卡」跑通，并证明推荐值得信任。

- 批量录入 + AI 自动打标（降低第一道门槛）
- 每日 3 套带理由的推荐，接天气 API 做**温度硬约束**
- 穿着打卡与搭配历史
- 数据模型扩展（衣物属性、搭配评分/策略/理由、穿着日志表、品牌按用户隔离）
- 界面文案全面中文化
- **门禁：录 20 件 < 5 分钟；推荐采纳率 ≥ 40%；7 日打卡率 ≥ 50%**

## Phase 2 — 越用越准（6–8 周）

**目标**：让系统从用户反馈中学习，推荐随使用时间变准。

- 反馈学习机制（采纳/拒绝/替换单品的信号回流到推荐权重）
- 体型与个人风格偏好入模
- 色值方案升级（更精确的色彩空间与配色判定，替代粗粒度色名）
- 补 PWA（可安装、基础离线）
- **门禁：第 4 周采纳率比第 1 周高 ≥ 10 个百分点**（学习是否真的有效，用数据说话）

## Phase 3 — 诊断与灵感（6–8 周）

**目标**：从「今天穿什么」延伸到「我的衣橱好不好、该怎么变化」。

- 衣橱诊断：单品利用率、闲置识别、结构缺口分析（缺什么才能多搭出几套）
- 灵感模板：可套用的搭配范式，解决「有衣服但没想法」
- 分享卡片：把每日搭配生成可分享图片
- **门禁：诊断被主动使用、灵感与分享有真实使用数据**（无人用则不投入 Phase 4）

## Phase 4 — 规模化（按需启动）

**目标**：在前三阶段验证成立后，才考虑「给更多人用」。

- 多用户支撑、性能与成本优化、必要的运营与数据看板
- 重新评估技术栈（是否仍以 Supabase 为核心，见 `docs/DECISIONS.md` ADR-002）
- **无固定排期**，由 Phase 3 的真实使用数据触发；在此之前不做任何「为了规模化」的架构改造
