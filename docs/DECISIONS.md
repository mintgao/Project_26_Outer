## ADR-001 不继承线上数据，从干净 schema 完全重构

- **日期**：2026-08-12
- **决策**：放弃现有线上数据，不做数据迁移。以干净的 schema 重建数据库基线，历史数据不导入。
- **背景与理由**：
  - 仓库内 migration 已被污染（`20240107_add_brands_and_ai.sql` 首行被误粘贴环境变量，SQL 无法执行），
    仓库 schema 与线上实际结构已经脱节，无法确认线上真实状态。
  - 现存数据基本是开发自测数据，业务价值极低。
  - 在 schema 不可信的前提下做迁移，成本与风险都远高于重新录入。
- **影响**：
  - Phase 0 需要重建 migration 基线（P0-05），可放心设计理想 schema，无历史包袱。
  - 用户需重新录入衣物（正好作为 P1-01「录 20 件 < 5 分钟」的真实验收场景）。
  - 从此**所有** schema 变更必须以 migration 文件进仓库，杜绝再次脱节。
- **状态**：已采纳

## ADR-002 Phase 1–3 继续使用 Supabase，Phase 4 再评估

- **日期**：2026-08-12
- **决策**：Auth / Postgres / Storage 继续使用 Supabase，不在 Phase 1–3 期间迁移或自建后端；到 Phase 4（规模化）再重新评估。
- **背景与理由**：
  - 单人开发、每周 10–15 小时，工程预算极其有限；Supabase 一套解决认证、数据库、对象存储，省下的是最稀缺的时间。
  - 当前瓶颈是「推荐是否被信任」这个产品问题，不是基础设施性能问题；过早自建是把精力花在错误的地方。
  - Postgres 本身是标准的，未来迁移成本可控。
- **影响**：
  - **代价：必须把 RLS 当代码维护** —— 所有 RLS 策略与表结构一起写进 migration 文件，
    禁止只在控制台点选；否则安全模型不可复现（P0-02、P0-03 即此原则的落地）。
  - 敏感逻辑（AI 调用、配额）必须放在 `api/` 服务端函数，不能依赖前端自律。
  - 需接受 Supabase 的用量与冷启动限制，作为已知约束而非缺陷。
- **状态**：已采纳

## ADR-003 目标端＝移动 Web 优先，Phase 2 末补 PWA

- **日期**：2026-08-12
- **决策**：只做移动优先的 Web 应用，**不做微信小程序、不做原生 App**；在 Phase 2 末期补 PWA（可安装、离线基础能力）。
- **背景与理由**：
  - 核心使用场景是「早上出门前掏出手机看一眼」，Web 已能满足；小程序与原生会带来平台审核、多端同步与额外维护成本。
  - 单人开发无法同时维护多端；一套代码 + Vercel 部署迭代最快。
  - PWA 能以极低成本换来「桌面图标 + 类原生启动」的体验，但它是体验优化，不是闭环前提，因此放在闭环验证之后。
- **影响**：
  - 所有 UI 必须按移动端窄屏优先设计，桌面端只需可用。
  - 相机/相册调用走 Web 标准 API，能力边界以浏览器为准。
  - PWA 相关工作（manifest、Service Worker、离线缓存策略）列入 Phase 2 末尾，不提前做。
- **状态**：已采纳

## ADR-004 保留 AI 但改定位：升级为「自动打标 + 主色提取」，且只在服务端调用

- **日期**：2026-08-12
- **决策**：保留 AI 能力，但从原来的「识别 3 个字段」升级为「自动打标 + 主色提取」，服务于录入效率与推荐质量。
  **所有模型调用一律只在服务端进行**，密钥不得出现在前端产物中；**禁止再用 `VITE_` 前缀命名服务端密钥**。
- **背景与理由**：
  - 录入摩擦是核心循环的第一道门槛；AI 自动打标能直接支撑「录 20 件 < 5 分钟」的目标。
  - 主色提取是配色与推荐规则的输入，属于推荐质量的基础数据，比多识别几个字段更有价值。
  - 历史上密钥以 `VITE_DASHSCOPE_API_KEY` 命名，该前缀会被 Vite 打进前端产物，等同于公开密钥——
    这是必须从命名规范层面根除的错误，而不是靠人记得小心。
- **影响**：
  - AI 调用统一走 `api/dashscope.js`，并需 JWT 校验与单用户日配额（P0-04），防止密钥被滥用刷量。
  - 环境变量改名为 `DASHSCOPE_API_KEY`；`.env.example` 与 Vercel 配置同步更新。
  - 前端只能调用自家 `api/` 接口，不得直连任何模型服务商。
  - AI 结果一律作为**可修改的建议**呈现，用户确认后入库，避免错误标签污染数据。
- **状态**：已采纳

## ADR-005 产品定位从「衣橱管理工具」改为「每日出门决策助手」

- **日期**：2026-08-12
- **决策**：产品定位改为**每日出门决策助手**。核心循环＝**录入 → 每日决策 → 打卡 → 学习**。
  衣橱数据是燃料，不是目的。
- **背景与理由**：
  - 「管理衣橱」本身不是用户的痛点，用户不会为了整理而整理；真正的痛点是「明天早上穿什么」。
  - 以「管理」为定位会导致成功标准变成「录入了多少件」，进而堆砌分类、标签、统计等无人使用的功能。
  - 以「决策」为定位，成功标准变成「推荐是否被采纳」，指标可测量、功能取舍有据可依。
- **影响**：
  - 首页必须是「今天穿什么」，不是衣橱列表。
  - 北极星指标为推荐采纳率与打卡率（Phase 1 门禁即由此而来），录入量只是辅助指标。
  - 所有新功能需回答「它如何提升今天这次决策的质量或降低决策成本」，否则不做。
  - README 与全站文案需相应调整，去掉「衣橱管理」式表述。
- **状态**：已采纳
